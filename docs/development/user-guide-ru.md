# Работа с Examiner: руководство для владельца fork

Документ ведётся по запросу U-001 от 2026-10-19. Рабочий журнал:
[work-log-ru.md](work-log-ru.md). Инструкции дополняются вместе с изменениями программы.

Первый запуск удобнее проходить по [наглядному маршруту для Windows](run-windows-ru.md):
схема действий, команды по шагам, ожидаемые результаты и работа в браузере.

## Как отслеживать работу

- U-001, U-002, … — последовательные запросы пользователя, начиная с запроса
  о нумерации и делегировании разработки. Более ранние сообщения не перенумерованы.
- A-001, A-002, … — сообщения помощника, включая промежуточные отчёты.
- D-001, D-002, … — записи о выполненных изменениях в журнале.
- Issue, PR и SHA коммита — постоянные указатели в GitHub и Git.

В отчётах указываются исходный запрос, результат, проверки и ограничения.
Планы и рабочие задачи ведутся в GitHub Issues согласно AGENTS.md;
журнал содержит факты выполнения и не заменяет трекер задач.

## Что можно поручить помощнику

В подключённой рабочей копии помощник может изучать код, создавать ветки,
редактировать файлы, выполнять проверки, делать коммиты и при доступных правах
отправлять ветки в fork и открывать PR. Пользователь описывает желаемое поведение
и смотрит результат, изменения и доказательства проверки.

Для каждой задачи помощник обновляет относящиеся к ней инструкции и журнал.
Сам по себе этот документ не предоставляет доступ к GitHub или компьютеру.
Работа выполняется во время активных заданий; постоянный фоновый мониторинг
этим чатом не обеспечивается.

Начальная схема: отдельная ветка на задачу, PR в Fail-404/examiner с базовой
веткой main. Слияние выполняется по поручению пользователя. Предложение изменений
автору pavelanni/examiner оформляется отдельно, с явно выбранной целью PR.

В новом чате попросите помощника прочитать AGENTS.md, CLAUDE.md и эти два документа.
Нумерацию продолжать по последним записям журнала и сообщениям текущей беседы.

## Где выполняются команды

| Место | Что доступно |
| --- | --- |
| Этот облачный сеанс | Копия /workspace/examiner и инструменты сеанса |
| Windows 10/11 и VS Code пользователя | Локальная копия и установленные на ПК инструменты |
| GitHub | Fork, история, Issues и PR |

Чат с облачной средой не управляет установленным на Windows VS Code.
Для непосредственного выполнения команд на ПК нужен агент в IDE с доступом
к открытой папке. Облачную и локальную копии синхронизируют через GitHub.

Сетевое разрешение на api.github.com и авторизация на GitHub — разные условия.
Чтение Git не доказывает право push или доступ API. Проверять нужные операции
через существующее подключение; ключи и токены в переписку не отправлять.

## От чьего имени выполняется работа

По запросу U-002 работа ведётся через GitHub-аккаунт Fail-404.
Перед публикацией проверять gh api user --jq .login: ожидается Fail-404.
Если текущая авторизация принадлежит другому аккаунту, публикацию не выполнять
до исправления подключения. GitHub API определяет автора созданного PR или Issue.

Авторство Git-коммитов задаётся отдельно. Для этого checkout настроены локально:

```powershell
git config --local user.name "Fail-404"
git config --local user.email "115959997+Fail-404@users.noreply.github.com"
```

Этот noreply-адрес построен по идентификатору 115959997, полученному от GitHub API
для текущего аккаунта Fail-404. Он не раскрывает личный email. Эти команды
можно повторить в локальной копии Windows. Они не входят в файлы проекта
и не меняют настройки остальных репозиториев. Проверка перед коммитом:

```powershell
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
```

Имя автора не является способом авторизации. Использование ИИ как инструмента
не требует менять автора коммита на OpenAI. Признак Verified относится к подписи
коммита; noreply-адрес сам по себе подпись не создаёт.

Два ранее опубликованных коммита 942baf1 и f01a2a3 имеют имя Emily и на момент
проверки не связаны GitHub с профилем пользователя. Исправление настройки
действует на последующие коммиты. Опубликованная история пока не переписывалась.

сохраняется и в fork; само по себе оно не указывает на ошибочную рабочую копию.

## Windows: получить копию

Установить Git for Windows, Go 1.26.x, VS Code и расширение Go.
Следующие команды выполняются в PowerShell при первоначальном получении копии:

```powershell
New-Item -ItemType Directory -Force "$HOME\Projects"
Set-Location "$HOME\Projects"
git clone https://github.com/Fail-404/examiner.git
Set-Location examiner
git remote add upstream https://github.com/pavelanni/examiner.git
git remote -v
code .
```

New-Item создаёт папку, Set-Location переходит в неё. Clone скачивает файлы
и историю. Origin обозначает fork, upstream — исходный проект автора.
Добавление upstream только сохраняет адрес. Code с точкой открывает текущую
папку в VS Code. Повторно клонировать поверх существующей копии не нужно.

## Windows: инструменты и сборка

Из папки проекта:

```powershell
go install github.com/a-h/templ/cmd/templ@v0.3.1020
go install github.com/go-task/task/v3/cmd/task@v3.45.4
$env:Path += ";$(go env GOPATH)\bin"
templ --version
task --version
go mod download
task build
task test
```

Go install устанавливает инструменты заданных версий. Изменение Path позволяет
текущему терминалу находить их; в новом терминале может понадобиться повторить
эту строку. Go mod download загружает зависимости. Task build генерирует шаблоны
и собирает bin/examiner.exe. Task test запускает go test ./... после генерации.
Это инструкция для Windows; полный цикл на ПК пользователя помощником не проверен.

## Windows: окончания строк и тесты

Два теста TestEvalPromptGoldenTrialExam и TestGradePromptGoldenTrialExam строго
сравнивают сгенерированные инструкции с файлами .golden. Они не требуют живого LLM.
Преобразование LF в CRLF может нарушить сравнение: часть перевода строк
формируется программно, часть берётся из файлов.

Диагностика без изменения файлов:

```powershell
git status --short
git ls-files --eol internal/llm/prompts internal/llm/testdata
```

I/lf относится к индексу Git, w/crlf — к файлу в рабочей папке.
Если у шести .txt в internal/llm/prompts/ и двух .golden в internal/llm/testdata/
стоит w/crlf, открыть соответствующие файлы в VS Code, нажать CRLF в строке
состояния, выбрать LF и сохранить. Уже использующие LF файлы менять не требуется.

```powershell
go test ./internal/llm -run 'Test(Eval|Grade)PromptGoldenTrialExam' -count=1
task test
```

Не использовать -update без осознанного изменения ожидаемого результата:
этот флаг перезаписывает эталоны. Механизм ошибки воспроизведён помощником
во временной Linux-копии; причина на конкретном ПК ещё не подтверждена.

## Запуск Examiner и управление

Нужен доступный OpenAI-совместимый LLM. Настройки EXAMINER_LLM_URL,
EXAMINER_LLM_MODEL и при необходимости EXAMINER_LLM_KEY должны соответствовать
выбранному сервису. По умолчанию используется Ollama на localhost:11434
и модель llama3.2. Сервер проверяет доступность API при старте.

Перед первым запуском задать EXAMINER_ADMIN_PASSWORD безопасным способом.
Пароль первого администратора используется при создании пользователей в пустой
базе; смена переменной не меняет пароль уже существующего администратора.

После настройки модели и пароля, в PowerShell из папки проекта:

```powershell
task run -- --addr 127.0.0.1:8080 --lang ru --questions questions/physics_ru.json --secure-cookies=false
```

Открыть браузер на локальном компьютере по адресу http://localhost:8080.
Это адрес собственного ПК, а не облачного сеанса. Войти как admin, создать
тестового студента, войти студентом, пройти экзамен и проверить результаты
под администратором. Для локального HTTP отключены Secure cookies.
Остановка сервера в его терминале: Ctrl+C. Данные сохраняются в examiner.db
в рабочей папке; повторный запуск использует эту базу. Базу и секреты не коммитить.
Эта инструкция ещё не подтверждает успешный запуск в текущей облачной среде.

## История, PR и самостоятельная работа

Небольшую задачу выполнять в отдельной ветке. Перед переходом между ветками
проверить git status и сохранить свои незавершённые изменения.

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c improve/short-name
```

Switch переключает ветку; -c создаёт новую. Pull обновляет локальную main
из fork; --ff-only останавливает операцию, если требуется слияние расходящейся
истории. При таком сообщении не применять force: сначала изучить расхождение.

После редактирования запустить подходящие проверки и посмотреть git diff.
В VS Code раздел Source Control показывает изменения файлов. Выбрать относящиеся
к задаче файлы, выполнить Stage, Commit, затем Publish Branch или Push.
На GitHub открыть PR, проверить base repository Fail-404/examiner и base main.
Указать результат изменения и выполненные проверки.

Для возврата к прежнему состоянию сначала открыть нужный коммит или PR
по ссылке из журнала и посмотреть разницу. Отмену опубликованного изменения
обычно оформлять новым коммитом через git revert после проверки зависимых правок.
Для собственного эксперимента создать отдельную ветку от нужного коммита.
Удаление рабочих файлов и переписывание опубликованной истории для этого не нужны.

## Как описывать задачу помощнику

Указать пользователя функции, текущее поведение, желаемый результат и пример
проверки. Например: «Студент на странице результатов должен видеть …;
сейчас отображается …; проверить на экзамене с двумя вопросами».

В ответ помощник связывает работу с U-ID и Issue, описывает изменения,
прикладывает проверки и обновляет это руководство и журнал. Пользователь
получает ветку/PR/коммит, когда они действительно созданы, а не предполагаются.
